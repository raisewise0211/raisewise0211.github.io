## 한 줄 요약

> ROS2 Nav2는 "경로 계획", "장애물 회피", "복구 행동" 같은 각 기능을 별도의 ROS2 Action 서버로 만들고, Behavior Tree는 그 서버들을 언제 어떤 순서로 호출할지 결정하는 "지휘자" 역할만 담당한다.

## 원인과 결과: 왜 Nav2가 BT를 채택했는가

ROS2의 대표적인 내비게이션 스택인 **Nav2**는 로봇을 목적지까지 이동시키는 복잡한 작업을 담당한다.
이 작업에는 "경로 계산", "장애물을 만나면 우회", "막히면 후진 후 재시도", "완전히 막히면 사용자에게 알림" 같은
다양한 대응 로직이 얽혀 있다.

**원인**: 예전 Nav2(구 ROS Navigation Stack)는 이런 복구 로직을 C++ 코드 안에 하드코딩했다. 새로운 복구 전략을
추가하거나 순서를 바꾸려면 매번 재컴파일이 필요했고, 로봇마다 다른 복구 전략(예: "이 로봇은 후진이 불가능하니
제자리 회전만 시도")을 적용하기도 어려웠다.

**결과**: Nav2는 세션 4에서 배운 것과 똑같은 이유로 **BT Navigator**를 도입했다. 내비게이션의 전체 로직을 XML
파일로 빼서, 로봇 종류나 임무에 따라 **XML 파일만 바꿔서** 완전히 다른 내비게이션 전략을 쓸 수 있게 만들었다.

---

## Nav2 BT Navigator의 구조

```
                    ┌───────────────────────────┐
                    │   BT Navigator (BT 실행기)  │
                    │  navigate_to_pose.xml 로딩  │
                    └─────────────┬─────────────┘
                                  │ Tick (여기서부터는 세션 1~8과 완전히 동일)
                                  ▼
                     RecoveryNode ── FollowPath 계열
                     ┌────────────┴────────────┐
              메인내비게이션시퀀스           복구행동(Fallback)
        ┌──────┬──────┬──────┐          ┌──────┬──────┐
     경로계산  경로추종  목표도달확인    후진   제자리회전   대기

각 리프(Leaf) 노드는 실제로는 "ComputePathToPose", "FollowPath" 같은
ROS2 Action 서버를 호출하는 커스텀 StatefulActionNode(세션 8)로 구현되어 있다.
```

즉 지금까지 배운 4대 노드(Control/Decorator/Action/Condition), Blackboard/Ports, XML, Decorator,
Reactive 실행모델, 커스텀 노드 개념이 **전부 그대로** Nav2 안에서 쓰이고 있다. Nav2를 배우는 것은 결국
BT 문법 위에 "로봇 내비게이션 도메인의 Action들"을 얹은 것뿐이다.

## 대표적인 디자인 패턴

### 패턴 1: RecoveryNode (재시도 + 복구 로직 결합)

Nav2가 자주 쓰는 패턴으로, 세션 5의 Decorator 개념을 확장한 것이다. "주 작업이 실패하면, 복구 행동을 한 번
수행하고 나서 주 작업을 다시 시도한다"는 논리를 하나의 노드로 캡슐화한다.

```
RecoveryNode(재시도 최대 6회)
 ├── 자식1: 주 작업 (예: FollowPath)
 └── 자식2: 실패 시 수행할 복구 행동 (예: ClearCostmap)

동작: 자식1 실패 → 자식2(복구) 실행 → 다시 자식1 재시도 → ... 최대 6회
```

### 패턴 2: 계층적 Fallback으로 복구 전략 다단계 구성

```
Fallback("복구전략")
 ├── Sequence: 살짝후진 후 재시도
 ├── Sequence: 제자리회전 후 재시도
 └── Sequence: 완전정지 후 사용자에게 알림 (최후의 수단)
```

세션 6의 "우선순위가 높은 것을 왼쪽에 둔다"는 원칙이 그대로 적용된다 — 가장 가벼운 복구(살짝 후진)를 먼저 시도하고,
그래도 안 되면 점점 더 강한 조치로 넘어간다.

## 안티패턴 (하지 말아야 할 것들)

**원인과 결과로 짚어보는 흔한 실수들**:

| 안티패턴 | 왜 문제가 되는가 |
|----------|------------------|
| **Condition 안에 시간이 오래 걸리는 센서 처리 넣기** | Condition은 즉시 끝나야 한다(세션 2). 센서 처리가 오래 걸리면 트리 전체의 Tick 주기가 느려져 다른 안전 로직도 함께 느려진다. |
| **하나의 거대한 Sequence에 모든 임무를 다 나열** | 세션 7에서 배운 모듈화 원칙 위반. 임무 하나가 바뀔 때마다 전체 트리를 다시 검토해야 한다. |
| **ReactiveSequence 안에 무거운 연산을 가진 Condition을 넣기** | ReactiveSequence는 매 Tick마다 그 Condition을 다시 실행한다(세션 6). 무거운 연산이면 CPU를 낭비하고 반응 속도가 느려진다. |
| **onHalted()를 비워두고 로봇 정지 처리를 안 함** | 세션 8에서 강조한 것처럼, 트리는 취소됐는데 로봇은 계속 움직이는 위험한 불일치가 생긴다. |

## Groot2로 Nav2 디버깅하기

세션 4에서 배운 Groot2 Monitor 모드는 Nav2 실전 디버깅의 핵심 도구다. 로봇이 "왜 갑자기 멈췄는지",
"왜 계속 같은 자리를 맴도는지" 같은 문제를, 코드를 뒤지지 않고 **트리 위의 색깔 변화**만으로 원인을 좁힐 수 있다.

```
실전 디버깅 흐름

1. Groot2를 실행 중인 로봇(ROS2)에 연결
2. 문제가 재현되는 순간의 트리 색상을 관찰
   예: RecoveryNode의 "복구행동" 쪽이 계속 빨강(FAILURE)으로 반복됨
       → "복구 로직 자체가 실패하고 있다"는 것을 즉시 알 수 있음
3. 해당 리프 노드(예: ClearCostmap)의 ROS2 로그를 그때서야 좁혀서 확인
```

이 방식은 "일단 전체 로그를 다 뒤진다"는 접근보다 훨씬 빠르다. **원인 후보를 트리 구조로 미리 좁혀놓고
로그는 마지막에 확인**하기 때문이다.

## 핵심 개념 정리

!!! tip "이 세션의 핵심 3가지"
    1. **Nav2 BT Navigator = 지금까지 배운 BT 문법 그대로 + 내비게이션 도메인 Action들** — 새로운 개념이 아니라 응용이다.
    2. **RecoveryNode = "실패하면 복구하고 재시도"를 캡슐화한 Nav2식 패턴** — 세션 5 Decorator 개념의 확장.
    3. **안티패턴은 대부분 "노드 타입의 역할을 어겼을 때" 생긴다** — Condition에 무거운 연산, 거대한 단일 Sequence, onHalted 누락 등.

## 복습 (15분)

### 매칭 문제

아래 안티패턴과 그 이유를 짝지어보세요.

```
① Condition 안에 무거운 이미지 처리 넣기
② 임무 10개를 하나의 Sequence에 다 나열
③ onHalted()를 비워둠

A. 트리는 취소됐는데 로봇은 계속 움직이는 위험한 불일치
B. 트리 전체 Tick 주기가 느려짐
C. 임무 하나 바뀔 때마다 전체를 다시 검토해야 함
```

??? success "정답"
    ① - B, ② - C, ③ - A

### 퀴즈

!!! question "Q1"
    RecoveryNode 패턴이 세션 5의 어떤 Decorator 개념을 확장한 것인가?

??? success "정답"
    Retry Decorator의 확장이다. 단순 재시도(Retry)에서 한 걸음 더 나아가, 재시도 전에 "복구 행동(자식2)"을
    한 번 수행하도록 결합한 패턴이다.

!!! question "Q2"
    Groot2로 디버깅할 때 "원인 후보를 트리 구조로 먼저 좁힌다"는 것이 로그만 보는 것보다 나은 이유는?

??? success "정답"
    전체 시스템 로그를 처음부터 다 뒤지는 대신, 색상으로 표시된 FAILURE/RUNNING 노드 위치를 보고 문제가 발생한
    구체적인 가지(브랜치)만 좁혀서 그 부분의 로그만 확인하면 되므로 디버깅 시간이 크게 줄어든다.

!!! question "Q3"
    ReactiveSequence 안에 무거운 연산을 가진 Condition을 넣으면 왜 문제가 되는가?

??? success "정답"
    ReactiveSequence는 매 Tick마다(초당 수십 번) 그 Condition을 처음부터 다시 실행하기 때문에, 연산이 무거우면
    CPU 자원을 낭비하고 트리 전체의 반응 속도가 느려진다.
