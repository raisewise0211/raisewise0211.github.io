# 왜 Behavior Tree인가? — FSM의 한계와 Tick의 탄생

    - **핵심 목표**: 유한상태기계(FSM)가 왜 한계에 부딪혔는지, 그 결과로 Behavior Tree가 어떻게 등장했는지 이해
    - **참고 자료**: [behaviortree.dev - Introduction](https://www.behaviortree.dev/), Game AI Pro (Behavior Tree 챕터)
    - **수학/수식**: 이번 세션에는 없음

---

## 한 줄 요약

> 상태(state)가 늘어날수록 상태 전이(transition)가 기하급수적으로 늘어나 유지보수가 불가능해지는 FSM의 문제를, Behavior Tree는 "상태"가 아니라 "우선순위를 가진 작업 트리"로 바꿔서 해결한다.

---

## 원인과 결과: 왜 이런 것이 필요했는가

로봇이나 게임 캐릭터에게 "다음에 뭘 할지"를 정해주는 가장 오래된 방법은 **유한상태기계(FSM, Finite State Machine)** 였다.
예를 들어 청소 로봇을 만든다고 하자.

- 상태: `대기`, `청소중`, `충전하러가기`, `장애물회피`, `사람발견시정지`
- 전이: "배터리 20% 이하면 대기→충전하러가기로 바꾼다" 같은 규칙

**문제의 원인**: 상태 개수가 `N`개면, 이론상 상태 사이의 전이 규칙은 최대 `N × (N-1)`개까지 필요할 수 있다.
상태가 5개일 때는 20개의 전이만 신경 쓰면 되지만, 상태가 20개로 늘어나면 전이는 최대 380개가 된다.
새로운 상태(예: "사람을 발견하면 인사하기") 하나를 추가할 때마다, 기존의 모든 상태에서 "이 상태로 갈지 말지"를 다시 검토해야 한다.

**결과**: 이것을 실무자들은 "spaghetti state machine(스파게티 상태기계)"라고 부른다. 상태와 전이선이 스파게티 면발처럼 얽혀서,
개발자 한 명이 상태 하나를 고치면 다른 상태 3개가 예상치 못하게 망가지는 일이 반복된다. 게임 업계(특히 Halo 2 AI 팀)와
로보틱스 업계는 2000년대 중반부터 이 문제를 반복적으로 겪었고, "전이 규칙을 일일이 나열하지 않고, 우선순위만 매겨서
자동으로 판단하게 하자"는 아이디어로 Behavior Tree가 만들어졌다.

**Behavior Tree가 이 문제를 해결하는 방식**: 상태 대신 **트리(나무 구조)**를 쓴다. 트리의 각 가지는 "이걸 먼저 시도해보고,
안 되면 다음 걸 시도해라" 같은 우선순위 규칙을 담고 있다. 새 행동을 추가하고 싶으면, 기존 가지들을 건드릴 필요 없이
트리에 가지 하나를 덧붙이기만 하면 된다. 이것이 BT가 "모듈적(modular)"이고 "확장 가능(scalable)"하다고 평가받는 이유다.

## FSM vs Behavior Tree 비교

```
FSM 방식 (상태 + 전이선)                    BT 방식 (우선순위 트리)
──────────────────────                     ──────────────────────

  [대기] ──배터리낮음──→ [충전하러가기]         [Root]
    │↑                        │↑                │
    │└──충전완료──────────────┘│           ┌────┴────┐
    │                          │        [배터리 낮음?]   [평소 행동들]
  [청소중] ──장애물──→ [회피]                  │
    │↑                  │↑                [충전하러가기]
    └──회피완료──────────┘

  ✗ 상태 늘어날수록 전이선 폭증           ✓ 가지 추가만 하면 됨
  ✗ 전이 규칙이 여기저기 흩어져있음       ✓ 우선순위가 트리 순서로 명확
  ✗ 디버깅 시 "지금 왜 이 상태인지" 추적 어려움   ✓ 트리를 눈으로 보면 순서가 바로 보임
```

## Tick이란 무엇인가

Behavior Tree는 "한 번 상태를 정하고 그 상태에 머무르는" FSM과 다르게, **아주 짧은 시간 간격(예: 0.1초)마다
트리 전체를 맨 위(Root)에서부터 다시 훑는다.** 이 "훑는 행위"를 **Tick**이라고 부른다.

- 매 Tick마다 Root는 자기 자식 노드에게 "너 Tick 받아라"라고 신호를 보낸다.
- 신호를 받은 자식은 자기가 할 일을 아주 잠깐 확인/실행하고, 그 결과를 부모에게 돌려준다.
- 이 과정이 트리 전체에 재귀적으로 퍼진다.

이렇게 "질문하듯이 자주 다시 확인한다"는 방식 덕분에, 로봇 앞에 갑자기 사람이 나타나는 것 같은 **예상치 못한 상황 변화**에
FSM보다 훨씬 자연스럽게 반응할 수 있다. FSM은 "지금 상태"만 기억하고 있다가 전이 조건이 만족될 때만 바뀌지만,
BT는 매 Tick마다 "지금 뭐가 제일 급한 일인지"를 처음부터 다시 판단하기 때문이다.

```
시간 흐름 →

FSM:   [청소중 상태 유지] → [청소중 상태 유지] → (배터리 20%됨) → [충전 상태로 전이]
                                                     ↑ 이 순간에만 판단

BT:    Tick → Tick → Tick → Tick → Tick → Tick → ...
       매번  매번  매번  매번  매번  매번
       "지금 제일 급한 게 뭐지?"를 처음부터 다시 확인
```

## 핵심 개념 정리

!!! tip "이 세션의 핵심 3가지"
    1. **FSM의 근본 문제는 "전이 규칙의 조합 폭발"** — 상태가 늘어날수록 관리해야 할 전이선이 기하급수적으로 늘어난다.
    2. **BT는 상태 대신 우선순위 트리를 쓴다** — 새 행동을 추가할 때 기존 가지를 건드릴 필요가 없다.
    3. **Tick은 "짧은 주기로 트리 전체를 다시 훑는 것"** — 그 덕분에 갑작스러운 환경 변화에 유연하게 반응한다.

### 빈칸 채우기

FSM에서 상태가 20개면 최대 전이 규칙은 몇 개까지 필요할 수 있는가? (공식: `N × (N-1)`)

??? success "정답"
    20 × 19 = **380개**. 이것이 FSM이 상태 수가 늘어날수록 유지보수하기 어려워지는 핵심 이유다.

### 퀴즈

!!! question "Q1"
    FSM과 비교했을 때 Behavior Tree가 "새로운 행동 추가"에 더 유리한 이유는 무엇인가?

??? success "정답"
    FSM은 새 상태를 추가하면 기존의 다른 상태들과의 전이 규칙을 모두 다시 검토해야 하지만,
    BT는 트리에 새로운 가지(branch)를 추가하기만 하면 되고 기존 가지의 로직을 건드릴 필요가 없기 때문이다.

!!! question "Q2"
    "Tick"이 하는 일을 한 문장으로 설명하라.

??? success "정답"
    아주 짧은 시간 간격마다 트리를 Root부터 아래로 재귀적으로 훑으면서, 각 노드가 지금 할 일을 확인/실행하게 만드는 신호이다.

!!! question "Q3"
    BT가 FSM보다 "예상치 못한 상황 변화"에 더 잘 대응하는 이유는?

??? success "정답"
    FSM은 전이 조건이 만족되는 그 순간에만 판단을 바꾸지만, BT는 매 Tick마다 "지금 제일 급한 일이 뭔지"를 트리 전체에서 처음부터 다시 판단하기 때문이다.
